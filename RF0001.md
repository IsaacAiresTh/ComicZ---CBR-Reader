Sim — e você tem razão. Eu tratei o **leitor** como uma funcionalidade posterior, quando na verdade, pelo objetivo do projeto, **ler CBR é o núcleo do produto**. Biblioteca, guias, favoritos etc. existem em grande parte para melhorar a experiência em torno da leitura.

Eu mudaria a arquitetura pensando nisso desde o primeiro momento.

## O produto seria, antes de tudo, um leitor de HQs

O fluxo principal deveria ser:

```text
                    USUÁRIO
                       │
                       ▼
                 ┌───────────┐
                 │ Biblioteca│
                 └─────┬─────┘
                       │
                       ▼
                  ┌─────────┐
                  │   HQ    │
                  │  .CBR   │
                  └────┬────┘
                       │
                       ▼
                ┌─────────────┐
                │    Reader   │
                │    React    │
                └──────┬──────┘
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
        Página atual        Progresso
             │                   │
             ▼                   ▼
       imagem da página      PostgreSQL
```

E isso muda bastante algumas decisões arquiteturais.

---

# 1. O CBR precisa ser tratado como arquivo, não como "HQ"

Uma HQ e o arquivo da HQ são coisas diferentes.

Eu teria algo conceitualmente assim:

```text
Comic
 ├── metadata
 │    ├── title
 │    ├── description
 │    ├── series
 │    ├── issue
 │    └── cover
 │
 └── ComicFile
      ├── filename
      ├── format
      ├── size
      ├── storageKey
      ├── pageCount
      └── status
```

Por exemplo:

```text
Comic
────────────────────
id: 123
title: Batman
issue: 1
series: Batman (2016)


ComicFile
────────────────────
id: 456
comicId: 123
format: CBR
size: 184 MB
pageCount: 32
status: READY
storageKey: comics/456/file.cbr
```

Isso permite futuramente que uma mesma HQ tenha:

```text
CBR
CBZ
PDF
```

sem destruir o modelo.

---

# 2. E o CBR não deveria ser enviado inteiro para o navegador

Essa é uma decisão importante.

Você **poderia** simplesmente fazer:

```text
Servidor
   │
   │ arquivo.cbr
   ▼
Navegador
```

e tentar fazer o JavaScript interpretar o CBR.

Mas eu não faria isso como arquitetura principal.

O fluxo que eu recomendaria é:

```text
                 .CBR
                  │
                  ▼
           ┌──────────────┐
           │   Backend    │
           │ processamento│
           └───────┬──────┘
                   │
             extrair imagens
                   │
          ┌────────┴────────┐
          ▼                 ▼
      page-001.jpg      page-002.jpg
          │                 │
          └────────┬────────┘
                   ▼
                Storage
                   │
                   ▼
                Reader
```

O navegador recebe **as páginas**, e não precisa entender o formato CBR.

---

# 3. O que é CBR na prática

Isso é até interessante para o projeto.

CBR normalmente é um arquivo RAR contendo imagens:

```text
Batman-001.cbr
       │
       ▼
┌──────────────────┐
│ arquivo RAR      │
├──────────────────┤
│ page001.jpg      │
│ page002.jpg      │
│ page003.jpg      │
│ page004.jpg      │
│ ...              │
└──────────────────┘
```

Então seu backend pode:

```text
.CBR
 ↓
RAR
 ↓
imagens
 ↓
páginas
```

E o leitor trabalha com:

```text
GET /pages/1
GET /pages/2
GET /pages/3
```

---

# 4. Mas não faça isso durante o upload HTTP

Por exemplo, seria ruim:

```text
POST /comics/upload
        │
        ▼
recebe 200 MB
        │
        ▼
extrai CBR
        │
        ▼
gera 40 imagens
        │
        ▼
responde HTTP
```

O usuário poderia ficar esperando vários segundos/minutos.

O correto seria:

```text
POST /comics/upload
        │
        ▼
arquivo salvo
        │
        ▼
job criado
        │
        ▼
HTTP 202 Accepted
        │
        ▼
       Worker
        │
        ▼
   processa CBR
        │
        ▼
      READY
```

Então o banco poderia ter:

```text
PROCESSING
```

e depois:

```text
READY
```

ou:

```text
FAILED
```

---

# 5. Isso significa que eu já colocaria uma arquitetura de Worker

Mesmo no MVP.

Não precisa de Kubernetes, Kafka, RabbitMQ, microsserviços etc.

Você pode começar com:

```text
┌──────────────┐
│    NestJS    │
│     API      │
└──────┬───────┘
       │
       ▼
    PostgreSQL
       │
       ▼
┌──────────────┐
│    Worker    │
│   Node.js    │
└──────┬───────┘
       │
       ▼
    Storage
```

Inicialmente o worker pode até ser **outro processo do mesmo projeto**.

Mais tarde:

```text
API
 │
 ▼
Redis / Queue
 │
 ├─────────────┐
 ▼             ▼
Worker 1     Worker 2
```

---

# 6. E o leitor precisa de uma API própria

Eu criaria um módulo:

```text
reader/
```

com endpoints como:

```http
GET /api/v1/comics/:comicId/reader
GET /api/v1/comics/:comicId/pages
GET /api/v1/comics/:comicId/pages/:page
PATCH /api/v1/comics/:comicId/progress
```

Por exemplo:

```http
GET /api/v1/comics/123/reader
```

poderia retornar:

```json
{
  "comic": {
    "id": 123,
    "title": "Batman #1"
  },
  "pages": 32,
  "currentPage": 17
}
```

O React então sabe:

```text
Total: 32 páginas
Página atual: 17
```

# 9. Uma coisa que eu faria para melhorar MUITO a experiência

Não obrigaria o usuário a esperar a HQ inteira ser processada para começar a ler.

Existem duas estratégias.

### Estratégia A — processamento completo

```text
Upload CBR
    ↓
extrai tudo
    ↓
READY
    ↓
usuário lê
```

É mais simples.

### Estratégia B — processamento sob demanda

```text
Upload CBR
    ↓
arquivo armazenado
    ↓
usuário abre
    ↓
extrai/carrega página necessária
```

É mais complexo.

Para o **MVP eu faria A**.

Depois você pode otimizar.


# 11. Eu converteria as páginas para WebP

Você não precisa necessariamente manter:

```text
page001.jpg
page002.jpg
...
```

Depois de extrair, poderia converter:

```text
JPG
 ↓
WebP
```

Isso pode reduzir bastante o tamanho transmitido para o navegador.

Mas eu faria isso como uma etapa do processamento:

```text
CBR
 ↓
RAR
 ↓
imagem
 ↓
resize/normalização
 ↓
WebP
 ↓
storage
```

# 12. E existe uma questão importante: direitos autorais

Como você quer disponibilizar HQs para seus amigos, eu faria a aplicação pensando em **uso privado e arquivos que vocês tenham direito de armazenar/compartilhar**.

A arquitetura pode suportar os arquivos, mas eu evitaria construir o produto com a premissa de hospedar/distribuir grandes catálogos comerciais sem autorização.

Isso também influencia bastante o futuro storage e a infraestrutura.

## O fluxo completo do produto

No final, eu imagino algo assim:

```text
                    ┌──────────────┐
                    │    Usuário   │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │    React     │
                    └──────┬───────┘
                           │
             ┌─────────────┼─────────────┐
             │             │             │
             ▼             ▼             ▼
          Catálogo      Biblioteca     Reader
             │             │             │
             └─────────────┼─────────────┘
                           ▼
                       NestJS API
                           │
              ┌────────────┼─────────────┐
              │            │             │
              ▼            ▼             ▼
         PostgreSQL     Storage        Queue
                                          │
                                          ▼
                                       Worker
                                          │
                                          ▼
                                    CBR → páginas
                                          │
                                          ▼
                                       Storage
```

**Agora sim eu considero essa arquitetura alinhada com o que você realmente quer construir.**

E eu faria o **primeiro milestone do projeto ser justamente o caminho crítico `upload CBR → processamento → abrir leitor → navegar páginas → salvar progresso`**. Se isso funcionar, você já tem o coração do produto; depois catálogo, favoritos, guias e recursos sociais podem crescer ao redor dele.
